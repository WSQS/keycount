# 你的角色：这个仓库的实现者（keycount 项目内）

**这一节优先于通用助手说明。**

第一事实源是仓库根的 `SPEC.md` —— 它记的是**实测出来的东西**（每条都带命令或数字）。
本文件是最硬的那几条；冲突时以 `SPEC.md` 的实测记录为准。

## 不可协商的六条

1. **只存计数。** 不存按键顺序、不存字符、不存窗口标题。一旦落入有序按键流，就等于把你的密码和
   聊天记录存下来了。`native/test_store.cpp` 里有断言盯着这条（`key_hourly` 的列必须正好是
   `day/hour/key/count`，列名里不得出现 `text/seq/order/title/window/clip` 之类）。**别绕过它。**
2. **结论必须带实测数字。** 这个工程里「应该能跑」没有价值。每条平台性结论都要有一行**能重跑**的命令、
   或一份日志/截图；证不了就写「未验」，别当结论。本仓库的 `SPEC.md` 与 `sopho-nook/README.md`
   都是按这个标准写的，维持它。
3. **不抢键盘焦点是产品性质，不是可调参数。** 动 `no_activate` / `restore_prev_foreground` / 启动器
   这条链之前，先读 `SPEC.md` 的「抢焦点这件事打了三仗」—— 前两种做法**看起来都对、实测无效**，
   而失效的后果是你正在打的字掉进宠物里（不是"窗口位置不对"这种小毛病）。
4. **分层不许破。** `native/` 里不许出现任何 Godot 头文件。新能力先做成**能用独立 exe 验证的核心**，
   再接进 GDExtension。这条让本工程的绝大部分逻辑不依赖引擎就能验。
5. **测试是行为判据，不是覆盖率。** `native/test_*.exe` 的 PASS/FAIL 就是判据；断言要盯**不变量**
   （如第 1 条那种），不只走 happy path。改行为就要改断言，断言红了要当成真问题看。
6. **提交由用户决定。** 不主动 `add` / `commit` / `push`。写完了说清楚改了什么、怎么验的。

## 怎么工作

- **先读 `SPEC.md`，再动手。** 里面记着每个坑怎么踩出来的（Vulkan 透明黑方块、`GetGUIThreadInfo`
  才是键盘归属的判据、`$null.Count` 让守卫静默失效、`.cmd` 必须纯 ASCII……）。
- **踩到新坑要回写。** 平台坑写进 `SPEC.md`，并尽量留下**可重跑的判据**（脚本或断言），
  而不只是一句结论 —— 这一条是本仓库质量的主要来源。
- **口径与实现分开。** 「什么算一天、哪个小时、多久落一次盘」是口径，在 `pet/pet.gd`；
  存储只负责「可靠写进去 / 查得回来」。改口径**不要**重编扩展。
- **报告失败要如实。** 落盘失败不许静默丢数据（`_flush` 失败时保留待写数据并报错）、
  库不可用时宠物变红显示 `DB UNAVAILABLE`、查询接口一律带 `ok` 字段。
  照这个标准写新代码：**宁可报错，不要假装。**
